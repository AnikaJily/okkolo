## 2.2. Проектирование структуры и архитектуры сайта

Проектирование структуры и архитектуры сайта «Окколо» выполнялось после анализа пользовательских сценариев, описанных в разделе 2.1, и направлено на обеспечение доступности информации, прозрачности навигации и возможности самостоятельного выполнения целевых действий — записи на мероприятие, ознакомления с направлениями деятельности арт-кластера и оформления заказа в шоуруме. В основу положены требования, сформированные на базе персон и карт пути пользователя (Customer Journey Map): минимизация числа шагов до целевого действия, предсказуемая структура разделов, разделение информационного и транзакционного контента, а также техническая возможность обновления материалов без привлечения разработчика.

### 2.2.1. Информационная архитектура сайта

Информационная архитектура определяет состав разделов, иерархию страниц и связи между ними. Для сайта «Окколо» выбрана модель с одной главной страницей-витриной и отдельными тематическими разделами второго уровня, что соответствует сценариям персон Ирины и Кирилла (быстрый доступ к афише), Романа (изучение направлений и мастерских) и Кати (краткое понимание миссии проекта на главной).

**Структура разделов:**

| Раздел | URL / якорь | Назначение |
|--------|-------------|------------|
| Главная | `/` | Hero-блок, описание проекта, направления, превью мероприятий |
| О проекте | `/#about` | Миссия, призыв к действию, кнопки поддержки и перехода к направлениям |
| Направления | `/#directions` | Карточки: кофейня, мастерские, мероприятия, шоурум |
| Мероприятия | `/events` | Каталог событий, фильтрация по типу |
| Карточка мероприятия | `/events/:id` | Подробности, запись |
| Шоурум | `/showroom` | Каталог товаров, корзина, оформление заказа |

Глобальная навигация (шапка и подвал) дублирует ключевые точки входа: «Главная», «Мероприятия», «Шоурум», «Мастерские» (якорь на блок направлений). Такое решение снижает когнитивную нагрузку: пользователь может перейти в нужный раздел с любой страницы без возврата на главную, что особенно важно для персоны Кирилла, ориентированной на быстрый поиск афиши.

С карточек направлений на главной предусмотрены прямые переходы: направление, связанное с мероприятиями, ведёт на `/events`, шоурум — на `/showroom`. Это устраняет лишний уровень вложенности и согласуется с CJM записи на мероприятие и сценарием изучения мастерских.

Контент, не требующий отдельной страницы (миссия, команда в будущем, партнёры для персоны Марины), на текущем этапе сосредоточен на главной и в подвале; расширение структуры отложено, чтобы не перегружать интерфейс на этапе MVP.

### 2.2.2. Логическая архитектура программного комплекса

Система спроектирована по трёхуровневой схеме «клиент — сервер приложений — база данных», что является стандартом для веб-приложений с разделением представления и данных (рис. — см. приложение с диаграммой «Архитектура информационной системы «Окколо»»).

**Уровень представления** — клиентское веб-приложение, реализованное на React и TypeScript с рендерингом на стороне клиента (CSR), собираемое средствами Vite. В браузере пользователя выполняется отрисовка интерфейса, маршрутизация между экранами (`/`, `/events`, `/events/:id`, `/showroom`), локальное хранение корзины, отправка HTTP-запросов к API. После сборки статические файлы размещаются на VPS под управлением веб-сервера Nginx (как альтернативная площадка поддержан Vercel); логика бизнес-процессов на этом уровне не выполняется.

**Уровень приложений** — Strapi (headless CMS на Node.js). Выполняет роль единого backend: REST API для чтения и записи сущностей, встроенная админ-панель для сотрудников проекта. Через Strapi управляются направления, мероприятия, товары шоурума, регистрации на события и заказы. Медиаконтент (фотографии) хранится средствами модуля Upload Strapi и отдаётся по URL вместе с JSON-ответами API.

**Уровень данных** — СУБД PostgreSQL, связанная со Strapi. В базе хранятся структурированные записи: тексты, даты, цены, статусы заказов, контактные данные при регистрации. Выбор PostgreSQL обусловлен требованиями к надёжности и масштабируемости при росте числа мероприятий и заказов.

Обмен между уровнями: браузер → Strapi по протоколу HTTP/HTTPS (REST); Strapi → PostgreSQL — SQL-запросы. Такая архитектура позволяет обновлять контент сайта через админ-панель без правки исходного кода фронтенда, что критично для некоммерческого проекта с ограниченными ресурсами на разработку.

### 2.2.3. Структура клиентского приложения

Клиентская часть организована по принципу модульности и повторного использования компонентов.

**Слои кодовой базы:**

- `components/layout` — оболочка сайта (Header, Footer);
- `components/sections` — смысловые блоки главной страницы (Hero, About, Directions, Events);
- `components/pages` — самостоятельные экраны (EventsPage, EventDetailPage, ShowroomPage);
- `components/ui` — примитивы интерфейса (Button, ImageActionCard, Sheet, IconButton);
- `components/cart` — корзина и оформление заказа;
- `data` — статические заглушки и конфигурация навигации;
- `lib` — интеграция со Strapi, преобразование данных, правила ссылок направлений;
- `context` — глобальное состояние корзины;
- `styles` — дизайн-токены, сброс стилей, глобальные правила.

Такое разделение обеспечивает слабую связанность: секции главной не обращаются к внутренней логике страницы шоурума, а обращение к API сосредоточено в модулях `lib/strapi.ts`, `lib/events.ts`, `lib/products.ts`, что упрощает сопровождение и тестирование.

**Модель данных (предметная область в Strapi):**

- *Direction* (направление) — заголовок, описание, изображение, ссылка;
- *Event* (мероприятие) — название, дата, описание, фото, ссылка на запись;
- *Product* (товар шоурума) — название, цена, категория, изображение, галерея;
- *Event registration* — заявка на участие в мероприятии;
- *Order* — заказ из шоурума (состав, доставка/самовывоз, контакты).

На клиенте типы данных описаны в TypeScript; при недоступности Strapi используются локальные fallback-данные из `data/`, что обеспечивает работоспособность интерфейса в режиме разработки и демонстрации.

### 2.2.4. Проектирование навигации и маршрутизации

Маршрутизация организована следующим образом: текущий путь (`pathname`) хранится в состоянии корневого компонента `App`, и по нему условным рендерингом выбирается нужный экран (выбор экрана выполняется на стороне клиента). Переходы между крупными разделами выполняются обычными ссылками с полной перезагрузкой страницы — отдельный маршрутизатор сознательно не подключается ради небольшого числа экранов, поэтому приложение не является классическим одностраничным сайтом (SPA). Для корректной отдачи приложения при прямом переходе по URL на сервере настроен SPA-fallback (Nginx `try_files` с переадресацией на `index.html`; на Vercel — аналогичное правило rewrite).

Якорные ссылки (`#about`, `#directions`) обеспечивают доступ к блокам главной с учётом фиксированной шапки (`scroll-margin-top`). Это учитывает сценарий Романа: переход к разделу «Наши направления» из меню или с кнопки «Узнать о проекте».

### 2.2.5. Адаптивность и сеточная структура

Структура макета спроектирована по принципу mobile-first с контрольными точками: 640 px (планшет), 1024 px (десктоп), 1280–1440 px (широкий экран). На главной при ширине от 1024 px блоки Hero и «О проекте» выстраиваются в две колонки; направления на узкой ширине — карусель со стрелками, на достаточной — сетка из четырёх карточек (container query по ширине секции). Единые боковые отступы (`--page-padding-x`) ступенчато увеличиваются на больших экранах для сохранения читаемости заголовков в блоке «О проекте».

### 2.2.6. Обоснование выбора технологий (архитектурный уровень)

| Компонент | Технология | Обоснование |
|-----------|------------|-------------|
| UI | React 18, TypeScript | Компонентный подход, типизация, распространённость |
| Сборка | Vite | Быстрая разработка и сборка |
| Backend | Strapi | Готовая админка, REST API, работа с медиа без написания backend с нуля |
| СУБД | PostgreSQL | Надёжное хранение для продакшена |
| Стили | CSS Modules + токены | Изоляция стилей, соответствие макету Figma |
| Хостинг фронта | VPS + Nginx | Единый сервер с CMS, полный контроль над окружением (Vercel — альтернатива) |

Отказ от отдельного сервера на Express и WebSocket обусловлен достаточностью REST для сценариев сайта: просмотр каталогов, формы записи и заказа не требуют постоянного двустороннего канала.

**Вывод по разделу 2.2.** Спроектирована информационная архитектура с главной-витриной и тематическими разделами, трёхуровневая логическая архитектура «React — Strapi — PostgreSQL», модульная структура клиентского приложения и правила маршрутизации, согласованные с пользовательскими сценариями и ограничениями инклюзивного проекта.

## 2.3. Проектирование пользовательского интерфейса

Проектирование пользовательского интерфейса сайта «Окколо» опирается на анализ потребностей разных групп пользователей, выполненный в разделе 2.1. Проект ориентирован на инклюзивную среду для молодых людей с инвалидностью и без, поэтому при разработке интерфейса учитывались не только информационные запросы, но и возможные барьеры взаимодействия с цифровым интерфейсом: контраст, размер шрифта, предсказуемость навигации, минимизация перегрузки экрана.

### 2.3.1. Принципы проектирования интерфейса

На основе персон и CJM сформулированы следующие принципы:

1. **Понятность с первого экрана** (Катя, Марина) — краткая формулировка миссии на главной, визуальный акцент на блоке «Окколо — инклюзивный социальный проект».
2. **Быстрый путь к действию** (Кирилл, Ирина) — кнопки «Записаться», «Подробнее», «В корзину» на карточках без скрытия за дополнительными меню.
3. **Доступность чтения** (Ирина) — достаточный контраст текста и фона, крупные заголовки, ограничение длины строки в текстовых блоках, отказ от мелкого серого текста в критичных местах.
4. **Мобильный приоритет** (Роман) — удобные зоны нажатия, карусель направлений на узком экране, выезжающее меню в шапке.
5. **Визуальная целостность** — единая шкала скруглений, цветов бренда (фиолетовый, жёлтый акцент), повторяющиеся паттерны карточек.

### 2.3.2. Дизайн-система и визуальный язык

Визуальный язык сайта согласован с фирменным стилем «Окколо» и зафиксирован в файле дизайн-токенов `styles/tokens.css`.

**Цвета:** фон страницы — светло-серый (`#f9f9f9`); поверхности карточек и шапки — белые; акцентные действия — фиолетовый (обводка `#c594e8`, заливка кнопок `#d5a7f6`); выделение ключевого сообщения — жёлтый (`#fedd5b`) в блоке «О проекте». Текст основной — чёрный; вторичный — единый серый (`#666666`) для иерархии.

**Типографика:** единое семейство Onest (начертания 500–600, fallback Inter / системный sans-serif) — пять ролей размеров (header-1/2/3, body, tag). Роли заданы переменными (`--text-body`, `--text-feature-title`, `--text-section-title`) с адаптивным увеличением на брейкпоинтах 640 и 1024 px.

**Радиусы и тени:** единая шкала `--radius-sm` … `--radius-xl` (10–20 px); карточки — `--radius-xl` (20 px), фото — `--radius-lg` (16 px); кнопки — pill-форма (`--radius-pill`, 40 px). Тени карточек — лёгкие, усиливаются при наведении для обратной связи.

**Компоненты UI-библиотеки проекта:**

- *Button* — варианты primary (заливка) и outline (контур); размеры sm, md, lg;
- *ImageActionCard* — карточка с изображением в режимах overlay (направления) и preview (мероприятия, товары);
- *Sheet* — боковая панель мобильного меню и корзины на базе Radix Dialog;
- *IconButton* — стрелки карусели, иконка меню.

Повторное использование компонентов снижает риск визуальной несогласованности и ускоряет вёрстку новых экранов.

### 2.3.3. Проектирование ключевых экранов

**Главная страница** объединяет шапку, hero-фотографию команды, блок «О проекте» (жёлтый акцент на заголовке, описание, кнопки «Поддержать проект» и «Узнать о проекте»), секцию «Наши направления», превью «Ближайшие мероприятия» с кнопкой перехода в полный каталог, подвал. На десктопе hero и текстовый блок выровнены в две колонки равной высоты; контент главной выровнен по центру в текстовом блоке для симметрии и спокойного восприятия.

**Раздел «Мероприятия»** — заголовок страницы, сетка карточек с датой, типом события, кнопками «Подробнее» и «Записаться». Модальное окно деталей и отдельная модалка записи разделены, чтобы не перегружать один экран (ответ на барьеры сложных форм из CJM).

**Карточка мероприятия** (`/events/:id`) — полное описание, визуал, призыв к записи.

**Шоурум** — hero-изображение, сетка товаров, модальное окно товара с галереей, плавающая кнопка корзины, панель оформления заказа с выбором самовывоза/доставки и расчётом стоимости доставки.

**Шапка сайта** — логотип, горизонтальное меню (десктоп), кнопка «Поддержать», бургер-меню (мобильные). Шапка оформлена как «плавающая карточка» со скруглением, визуально отделена от фона.

**Подвал** — логотип, слоган, навигация, контакты (e-mail), кнопка поддержки, копирайт; структура повторяет шапку для закрытия сценариев поиска контактов (Кирилл, Марина).

### 2.3.4. Инклюзивные аспекты интерфейса

С учётом персоны Ирины (слабовидение) в проекте заложены:

- контрастные пары «текст — фон» в основных блоках;
- крупные заголовки секций и карточек (`--text-feature-title`);
- семантическая разметка (`header`, `nav`, `main`, `section`, заголовки `h1`–`h3`);
- текстовые подписи к интерактивным элементам (`aria-label` у кнопок-иконок);
- фокусные состояния (`focus-visible`) у ссылок и кнопок для навигации с клавиатуры.

Направления дальнейшей доработки по результатам CJM: расширенные `alt`-описания фотографий, явный блок о физической доступности пространства для персоны Романа, отдельная страница для партнёров (персона Марина).

### 2.3.5. Паттерны взаимодействия

- **Карусель направлений** — горизонтальная прокрутка со стрелками при нехватке ширины; на широком экране — сетка без скрытия контента.
- **Модальные окна** — затемнение фона, закрытие по кнопке и клавише Escape (Radix).
- **Корзина** — выезжающая панель справа, сохранение состава в `localStorage` между сессиями.
- **Формы** — вертикальное расположение полей, крупные кнопки отправки, сообщения об успехе/ошибке.

### 2.3.6. Адаптивное поведение интерфейса

Интерфейс спроектирован с расчётом на смартфон как основное устройство персоны Романа. На мобильных устройствах: одноколоночная компоновка, полноширинные кнопки в блоке «О проекте», карусель вместо сетки направлений. На планшете и десктопе увеличиваются отступы, появляется многоколоночная сетка мероприятий и товаров, двухколоночный hero-блок. Ступенчатое изменение `--page-padding-x` предотвращает обрезание длинных заголовков в узкой колонке about-блока.

**Вывод по разделу 2.3.** Спроектирован интерфейс на основе дизайн-системы с токенами бренда «Окколо», набора переиспользуемых компонентов и экранов, согласованных с персонами и картами пути пользователя; заложены базовые инклюзивные практики и адаптивное поведение.

## 2.4. Прототипирование

Прототипирование — этап перевода проектных решений в проверяемые модели интерфейса до и в процессе реализации. Для сайта «Окколо» применялся итеративный подход: от структурных схем и макетов в Figma к интерактивному прототипу в коде.

### 2.4.1. Цели и задачи прототипирования

Задачи этапа:

- проверить информационную архитектуру на соответствие CJM (запись в мастерскую, запись на мероприятие);
- согласовать визуальный стиль с заказчиком (проект «Окколо»);
- выявить барьеры доступности на ранней стадии;
- получить основу для программной реализации с минимальными переделками.

### 2.4.2. Этапы прототипирования

**Этап 1. Низкодетализированные wireframe (каркасные прототипы).**

На основе CJM и структуры разделов построены схемы экранов: главная (блоки hero, about, directions, events), список мероприятий, карточка события, шоурум с корзиной. На этом уровне зафиксированы состав блоков, порядок скролла, расположение навигации и призывов к действию без финальной графики. Wireframe позволили убедиться, что путь Романа к разделу направлений не превышает два клика из меню, а путь Ирины к записи на мероприятие — три клика (главная → мероприятия → запись).

**Этап 2. Визуальный макет (high-fidelity) в Figma.**

По согласованным wireframe выполнены макеты с фирменными цветами, типографикой Onest, фотографиями пространства и команды. Макеты мобильной и десктопной ширины задали точные отступы, размеры карточек направлений (в т.ч. соотношение сторон изображения), стили кнопок и модальных окон. Макет Figma выступил эталоном для переноса в CSS-токены и компоненты React.

**Этап 3. Интерактивный программный прототип (MVP).**

Реализован рабочий прототип на React + Vite с подключением Strapi API (либо статических заглушек при отсутствии сервера). Прототип включает:

- навигацию по разделам;
- загрузку направлений, мероприятий и товаров из API;
- модальные окна деталей и записи на мероприятие;
- корзину и отправку заказа (`POST /api/orders`);
- регистрацию на событие (`POST /api/event-registrations`).

Программный прототип позволяет проверить реальное поведение на устройствах, скорость загрузки, удобство форм и работу карусели — то, что невозможно полностью оценить в статичном Figma.

### 2.4.3. Соответствие прототипа пользовательским сценариям

| Сценарий (персона) | Решение в прототипе |
|--------------------|---------------------|
| Запись на мероприятие (Ирина, Кирилл) | Страница `/events`, кнопка «Записаться», модалка с полями |
| Изучение мастерских (Роман) | Блок «Направления», карточка «Мастерские», переход по «Подробнее» |
| Быстрое понимание проекта (Катя) | Hero + жёлтый блок с формулировкой миссии на главной |
| Покупка в шоуруме | `/showroom`, корзина, оформление заказа |
| Поддержка проекта (все) | Кнопка «Поддержать» в шапке, about, подвале (mailto) |

По результатам сопоставления с CJM 1 (мастерская) в прототип заложена навигация на направления; полноценный раздел с описанием доступности помещения запланирован как развитие после MVP. По CJM 2 (мероприятие) разделены модалки «Подробнее» и «Записаться», увеличен контраст карточек, заголовки переносятся до трёх строк для читаемости.

### 2.4.4. Итерации и уточнения

В ходе реализации прототипа выполнены уточнения:

- переход с жёсткой сетки направлений на карусель при узкой ширине с сохранением минимальной ширины карточек;
- выравнивание кнопок в карточках мероприятий по нижнему краю сетки;
- единый компонент `Button` в модальных окнах товара;
- добавление подвала с навигацией и контактами;
- ступенчатое уменьшение боковых отступов на промежуточных разрешениях для сохранения целостности заголовка в блоке «О проекте»;
- привязка карточек направлений «Шоурум» и «События» к страницам `/showroom` и `/events`.

Каждая итерация проверялась в браузере на ширинах 375, 768, 1280 и 1440 px.

### 2.4.6. Ограничения прототипа и план развития

Текущий прототип не включает: личный кабинет пользователя, онлайн-оплату, раздел для партнёров, полноценный блок о физической доступности здания, многоязычность. Эти функции выходят за рамки MVP и могут быть реализованы на следующем этапе развития сайта.

## Выводы по главе 2

В главе 2 выполнено комплексное проектирование веб-сайта инклюзивного социального проекта «Окколо» — от анализа аудитории и пользовательских сценариев (раздел 2.1) до архитектуры, интерфейса и прототипов.

На этапе анализа с применением методов персон и Customer Journey Map выявлены потребности посетителей с различными ограничениями и без них, определены барьеры: недостаток информации о доступности пространства, сложность записи, слабая читаемость интерфейса, неочевидная структура для партнёров.

На основе анализа спроектирована информационная архитектура с главной страницей-витриной и разделами «Мероприятия» и «Шоурум», согласованная с глобальной навигацией. Логическая архитектура построена по трёхуровневой модели: клиентское приложение на React, сервер Strapi с REST API, база данных PostgreSQL. Клиентская часть разделена на модули layout, sections, pages, ui, что обеспечивает сопровождаемость кода.

Спроектирован пользовательский интерфейс на основе дизайн-системы с CSS-токенами бренда, переиспользуемых компонентов и адаптивной вёрстки mobile-first. Учтены инклюзивные требования: контраст, крупная типографика, доступность с клавиатуры, понятные сценарии записи и заказа.

Прототипирование проведено в три этапа — от wireframe до интерактивного MVP с интеграцией Strapi. Прототип покрывает ключевые сценарии записи на мероприятие, ознакомления с направлениями и покупки в шоуруме и может быть использован для демонстрации на защите выпускной квалификационной работы.

Результаты главы 2 формируют основу для главы 3 «Реализация и тестирование сайта», где описываются детали программной реализации, развёртывание и проверка качества разработанного решения.
