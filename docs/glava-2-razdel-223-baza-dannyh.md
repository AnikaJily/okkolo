Для хранения данных сайта «Окколо» спроектирована реляционная база данных. На рабочем сервере она работает под управлением СУБД PostgreSQL 16 (выбор обоснован в подразделе 2.2.2), в среде разработки — под управлением SQLite, на структуру данных это не влияет. Схему базы не пришлось писать вручную на SQL: каждый тип данных описан в CMS Strapi отдельным файлом `schema.json` (всего таких описаний 18), а при запуске Strapi сам создаёт и обновляет таблицы PostgreSQL по этим файлам. Поэтому логическая модель данных (то, какие есть сущности, их поля и связи) и физическая (реальные таблицы PostgreSQL) всегда совпадают. Логическая модель базы показана на ER-диаграмме (рисунок 4).

На диаграмме каждая сущность изображена прямоугольником с перечнем её полей; отдельно отмечены первичный ключ (PK), внешние ключи к файлам (FK) и уникальное поле (UK) `slug` у мероприятия. Связи показаны линиями между сущностями, а их кардинальность подписана у концов линий: «1» — одной записи соответствует ровно одна, «N» — много записей, «0..1» — ноль или одна (необязательная связь). Тип линии уточняет, чем связь закреплена: сплошная — «жёсткая» связь через внешний ключ (так все записи связаны с файлами), пунктирная — «мягкая» связь без внешнего ключа, через текстовое поле или JSON (так мероприятие связано с заявками, а товар — с заказом).

Всего выделено 18 сущностей. По способу хранения они делятся на коллекции (множество записей — 14 сущностей: направления, мероприятия, товары, позиции меню, программы мастерских, отчёты, документы, фотогалереи, заявки и заказы) и одиночные типы (одна запись на весь сайт — 4 сущности: страницы «О нас», «Доступность», «Мастерские» и постеры меню кофейни). Главные для проекта — мероприятия, товары и порождаемые ими заявки и заказы; остальные сущности хранят контент сайта и отчётность организации.

Первичный ключ каждой таблицы — числовой идентификатор `id`, который СУБД присваивает автоматически: он не меняется при редактировании данных, компактен, по нему автоматически строится индекс для быстрого поиска и не несёт лишнего смысла (телефон или почту как ключ использовать нельзя — они не уникальны и со временем меняются). У мероприятия есть ещё и уникальное поле `slug`, по которому строится понятный адрес страницы вида `/events/<slug>`. Для полей с заранее известным списком значений (тип мероприятия, категория товара, статус заказа и подобных) использован тип `enum`: он работает как ограничение CHECK и не пропускает значение, которого нет в списке. Кроме описанных полей, Strapi добавляет к каждой таблице служебные — дату создания, дату изменения и поля режима «черновик / публикация», благодаря которому сотрудник готовит материал как черновик и публикует его отдельным действием.

Главная особенность схемы в том, что между основными сущностями нет связей через внешний ключ: ни в одном из 18 описаний `schema.json` нет поля типа `relation`. Единственная «жёсткая» связь — связь записей с файлами (картинками и PDF): их хранит встроенный механизм Strapi в служебных таблицах, причём один файл может относиться сразу к нескольким записям. Остальные связи сделаны «мягко». Мероприятие и заявка на него связаны как «один ко многим», но без внешнего ключа — заявка хранит идентификатор мероприятия в обычном текстовом поле и копию его названия. Товар и заказ по смыслу связаны как «многие ко многим»; вместо отдельной таблицы «позиции заказа» весь состав заказа сохраняется прямо в заказе, в поле `items` в формате JSON. Заявка на мастерскую вообще ни с чем не связана: форма обратного звонка работает сразу для всех программ. Часть группировок (отчёты, документы, позиции меню) тоже сделана не связями, а значениями полей.

Справочные таблицы (направления, мероприятия, товары, меню, отчёты, страницы) приведены к третьей нормальной форме: поля хранят по одному значению, первичный ключ простой, лишних зависимостей между полями нет. Заявки и заказы намеренно денормализованы, и это осознанное решение: они должны запоминать данные такими, какими те были в момент оформления, а не подтягивать их из справочника. Если мероприятие переименуют или удалят, уже поданная заявка сохранит старое название; если у товара изменится цена, в заказе останется цена на момент покупки. Поэтому заявка хранит копии идентификатора и названия мероприятия, а заказ — весь состав с ценами в поле `items` (которое формально нарушает 1НФ, но это сознательный компромисс ради сохранности истории, а не ошибка). Отсутствие внешнего ключа заодно делает приём заявок устойчивым — заявку можно принять, даже если мероприятие уже удалили. Для проекта на старте, с небольшим объёмом данных, такой подход проще и надёжнее, а при росте схему можно достроить: добавить таблицу «позиции заказа» и связи через внешние ключи, оставив копии данных как историю.

Готовую логическую модель Strapi при запуске сам разворачивает в физическую — таблицы PostgreSQL: создаёт таблицы, задаёт типы столбцов (текст, число, дата, логический тип, формат JSON), добавляет служебные поля и таблицы для хранения файлов. Отдельный SQL-листинг приводить не нужно — он формируется автоматически, а источником истины служат файлы `schema.json`, по которым построена диаграмма. Работа серверной части с этой базой описана в подразделе 3.2.
