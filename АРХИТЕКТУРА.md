# Архитектура проекта «Окколо» — простыми словами

Этот файл — шпаргалка по проекту для защиты перед преподавателем. Читать сверху вниз, в конце есть готовые ответы на вопросы.

---

## Часть 1. Что это вообще такое

«Окколо» — инклюзивный социальный проект в Краснодаре. Кофейня + мастерские (швейная, кофейное дело, звукорежиссура) + шоурум с изделиями + площадка для мероприятий. Цель — пространство, где работают и общаются люди с инвалидностью и без.

Мы сделали для них **сайт-визитку с админкой**:
- посетитель заходит на сайт, смотрит мероприятия и товары, может оставить заявку;
- сотрудники проекта через админ-панель добавляют новые мероприятия и товары без программиста.

## Часть 2. Из чего состоит проект

Проект состоит из **трёх независимых частей**, которые живут на одном сервере, но общаются между собой как разные программы.

```
┌────────────────────────────────────────────────────────────────┐
│                  Один сервер (VPS) 158.160.128.16              │
│                                                                │
│  1. ФРОНТ              2. БЭКЕНД (CMS)        3. БАЗА ДАННЫХ   │
│  ───────────           ───────────────        ──────────────   │
│  Сайт «Окколо»         Strapi 5                PostgreSQL 16   │
│  (HTML, CSS, JS)       (Node.js)               (хранилище)     │
│                                                                │
│  Раздаёт картинки      Принимает запросы       Хранит все      │
│  и страницы            от сайта,               данные:         │
│                        отдаёт данные,          мероприятия,    │
│                        обслуживает админку     товары и т.д.   │
│                                                                │
│         ▲                    ▲                      ▲          │
│         │                    │                      │          │
│         │    HTTP-запросы    │   SQL-запросы        │          │
│         │    через nginx     │                      │          │
│         └────────────────────┴──────────────────────┘          │
└────────────────────────────────────────────────────────────────┘
                              ▲
                              │
                              │ HTTP (порт 80)
                              │
            ┌─────────────────┴──────────────────┐
            │  Браузер посетителя или сотрудника │
            │  (Chrome, Safari на телефоне)      │
            └────────────────────────────────────┘
```

### Что это значит человеческим языком

- **Фронт** — это то, что человек видит в браузере: тексты, картинки, кнопки. Готовый «слайд-шоу из HTML».
- **Бэкенд (CMS)** — это «программа-кладовщик». Сайт у неё спрашивает «дай мне мероприятия» — она достаёт из базы и отдаёт.
- **База данных** — это «склад» в виде таблиц (как Excel, только большой и быстрый).

Эти три части разделены не просто так. Например, можно завтра переписать сайт на другой технологии, но кладовщика и склад не трогать — данные останутся.

## Часть 3. Технологии и зачем каждая

### Фронт

| Технология | Что это | Зачем |
|---|---|---|
| **React 18** | библиотека для интерфейсов | удобно собирать страницу из маленьких кусочков-компонентов (кнопка, карточка, модалка) |
| **TypeScript** | JavaScript + типы | компьютер заранее ругается на ошибки («ты передал число вместо строки»), мы не ждём пока сайт сломается у пользователя |
| **Vite** | сборщик | превращает наш код в один маленький JS-файл, который браузер быстро загружает |
| **Tailwind 4** | CSS-фреймворк | вместо `style.css` пишем классы прямо в HTML: `class="text-lg font-bold p-4"` — быстрее и меньше мусора |
| **CSS Modules** | модульный CSS | когда стилей много, мы пишем их в отдельный файл `Card.module.css`, и они не «протекают» в другие компоненты |
| **Radix Dialog** | готовые модалки | окно «Записаться на мероприятие» — это не самопал, а проверенный компонент, который правильно работает с клавиатурой и screen-reader'ами |
| **Embla Carousel** | карусель | блок «Наши направления», который можно листать пальцем |
| **vite-imagetools** | оптимизация картинок | автоматически конвертирует JPG в современные форматы AVIF и WebP — сайт грузится в 3 раза быстрее на мобильных |

### Бэкенд

| Технология | Что это | Зачем |
|---|---|---|
| **Strapi 5** | готовая CMS | не пишем админку с нуля — Strapi даёт интерфейс «добавить мероприятие, заполнить поля, нажать сохранить» |
| **Node.js 20** | среда для JS на сервере | то же самое, что в браузере, только запускает наш бэкенд |
| **PostgreSQL 16** | база данных | хранит таблицы: мероприятия, товары, заявки, заказы |

### Инфраструктура

| Технология | Что это | Зачем |
|---|---|---|
| **Nginx** | веб-сервер | принимает все запросы извне и решает: статика → отдать сразу, `/api/...` → переслать в Strapi |
| **pm2** | менеджер процессов | следит, чтобы Strapi не упал. Если упал — перезапустит. Если сервер ребутнули — запустит Strapi автоматически |
| **GitHub Actions** | автоматизация деплоя | когда мы пушим код, оно само загружает его на сервер и перезапускает что нужно |
| **Ubuntu 24.04** | операционка | стандартный Linux для серверов |

> Версии здесь огрублены до мажорных для простоты. Точные патч-версии всех библиотек — в `DIPLOMA.md §3` (там полная semver-таблица). Этот файл их сознательно не дублирует, чтобы числа не разъезжались.

## Часть 4. Как данные ходят между всеми этими частями

Разберём на примере: пользователь зашёл на сайт и видит блок «Ближайшие мероприятия».

```
1. Пользователь:
   "хочу зайти на сайт okkolo"
                │
                ▼
2. Nginx:
   "пришёл запрос на /, это статика → отдаю index.html и main.js"
                │
                ▼
3. Браузер пользователя:
   получил HTML и JS, запустил React.
   React видит, что нужны мероприятия → делает fetch:
   GET http://158.160.128.16/api/events
                │
                ▼
4. Nginx:
   "пришёл запрос на /api/... → проксирую в Strapi на 127.0.0.1:1337"
                │
                ▼
5. Strapi:
   "хотят events? пойду в PostgreSQL"
                │
                ▼
6. PostgreSQL:
   "вот тебе таблица events: 13 записей" → возвращает Strapi
                │
                ▼
7. Strapi:
   преобразует в JSON и отдаёт обратно через nginx в браузер
                │
                ▼
8. React в браузере:
   получил JSON → построил 3 карточки → показал пользователю
```

**Главное:** все три части (браузер ↔ Strapi ↔ Postgres) общаются друг с другом через стандартизированные протоколы. Если что-то одно поменять — остальное не сломается, лишь бы протокол остался прежним.

### Что если CMS упал?

В коде фронта есть **запасной план** — `silent fallback на моки`. В папке `src/data/` лежат заранее заготовленные данные (3 примерных мероприятия, несколько товаров). Если запрос в Strapi падает — фронт молча показывает эти моки. Пользователь не видит ошибки, видит хоть какой-то контент. Это специально, не баг.

## Часть 5. Структура папок (фронт)

Фронт лежит в репозитории `okkolo`. Главные папки:

```
okkolo/
├── src/                          ← весь код тут
│   ├── App.tsx                   ← главный компонент, решает какую страницу показать
│   ├── main.tsx                  ← точка входа, React монтируется в HTML
│   │
│   ├── components/               ← все компоненты разбиты по типу
│   │   ├── ui/                   ← маленькие универсальные (Button, Sheet, Picture)
│   │   ├── layout/               ← Header и Footer
│   │   ├── sections/             ← блоки главной (Hero, About, Directions, Events)
│   │   ├── pages/                ← отдельные экраны (EventsPage, ShowroomPage и т.д.)
│   │   └── cart/                 ← корзина (плавающая кнопка + панель сбоку)
│   │
│   ├── context/CartContext.tsx   ← глобальная корзина (товары, которые добавил юзер)
│   │
│   ├── data/                     ← моки — данные на случай если CMS недоступен
│   │
│   ├── lib/                      ← вспомогательные функции
│   │   ├── strapi.ts             ← запросы к CMS (fetch /api/events и т.д.)
│   │   ├── events.ts             ← маппинг данных Strapi в наш формат
│   │   ├── delivery.ts           ← расчёт доставки (Краснодар / Россия)
│   │   └── ...
│   │
│   ├── styles/
│   │   ├── tokens.css            ← дизайн-токены (цвета, шрифты, отступы)
│   │   ├── reset.css             ← обнуление дефолтных стилей браузера
│   │   └── global.css            ← объединяющий файл
│   │
│   └── assets/images/            ← логотип, иконки, hero-фото команды
│
├── public/                       ← статические файлы (favicon)
├── index.html                    ← HTML-обёртка для React
├── package.json                  ← список зависимостей и команды
├── tsconfig.json                 ← настройки TypeScript
├── vite.config.ts                ← настройки сборщика
└── .github/workflows/deploy.yml  ← рецепт автодеплоя
```

### Логика «один компонент = одна папка»

Каждый компонент живёт в своей папке с тремя файлами:

```
Button/
├── Button.tsx          ← код компонента
├── Button.module.css   ← его стили
└── index.ts            ← экспорт, чтобы импортировать как from '@/components/ui/Button'
```

Это удобно потому что:
- всё связанное с Button лежит рядом;
- можно перетащить папку в другой проект и она работает;
- стили `.module.css` не «протекут» в другие компоненты (имена классов автоматически уникальные).

### Маршруты сайта

Сайт состоит из **9 маршрутов**:

| URL | Что показывает |
|---|---|
| `/` | Главная: hero-фото, описание проекта, направления, ближайшие 3 события |
| `/events` | Все события с фильтром по дате |
| `/events/:id` | Подробности конкретного события |
| `/showroom` | Каталог товаров с фильтром по категории + корзина |
| `/workshops` | Подробное описание мастерских (швейная, кофейное дело, звукорежиссура) |
| `/cafe` | Меню кофейни (фото + текстовая версия) |
| `/accessibility` | Доступность здания и сайта |
| `/about` | Подробно о проекте «Окколо» |
| `/reports` | Годовые отчёты и документы НКО |

Переключение между страницами — обычные `<a href="...">`, **полная перезагрузка**. Никакого React Router нет (сознательно).

**Почему без роутера?** Страниц немного, переходы между ними редкие. Роутер — это библиотека ~30 КБ. Для такого сайта это перебор. Перезагрузка между разделами не раздражает, а код проще.

## Часть 6. Структура CMS (Strapi)

CMS лежит в **отдельном репозитории** `okkolo-cms`. У них общий сервер, но разный код.

```
okkolo-cms/
├── src/
│   ├── api/                       ← каждая папка = одна «сущность» (Content Type)
│   │   ├── direction/             ← Направления (Кофейня, Мастерские, ...)
│   │   ├── event/                 ← Мероприятия
│   │   ├── product/               ← Товары
│   │   ├── showroom/              ← Настройки страницы шоурума (hero-картинка)
│   │   ├── order/                 ← Заказы (заполняется когда юзер оформляет корзину)
│   │   └── event-registration/    ← Заявки на мероприятие
│   │
│   ├── index.ts                   ← код, который запускается при старте Strapi
│   └── bootstrap-seed.ts          ← наливает mock-данные если коллекции пусты
│
├── config/                        ← конфигурация
│   ├── database.ts                ← подключение к Postgres (на сервере)
│   ├── server.ts                  ← порт, хост, режим прокси
│   ├── admin.ts                   ← секреты для админ-панели
│   └── middlewares.ts             ← CORS, безопасность, логи
│
└── .github/workflows/deploy.yml   ← автодеплой CMS
```

### Что такое «Content Type»

В Strapi каждая сущность данных описывается JSON-схемой. Например, мероприятие (`event/content-types/event/schema.json`):

```json
{
  "attributes": {
    "title": { "type": "string" },
    "date": { "type": "datetime" },
    "photo": { "type": "media" },
    "isPaid": { "type": "boolean" },
    "Price": { "type": "integer" },
    "type": {
      "type": "enumeration",
      "enum": ["музыка", "мастер-класс", "лекция", "стенд-ап"]
    },
    "spotsTotal": { "type": "integer" }
  }
}
```

Strapi читает эту схему и **сам**:
1. Создаёт таблицу `events` в Postgres с нужными колонками;
2. Делает форму в админке для заполнения;
3. Создаёт REST API: `GET /api/events`, `POST /api/events`, `PUT /api/events/:id`, `DELETE /api/events/:id`.

Никакого кода не надо писать. Сотрудники проекта в админке заполняют форму, нажимают «опубликовать» — и через секунду новое мероприятие появляется на сайте.

### Какие сущности есть в нашей CMS

Всего в CMS **17 типов контента**; ниже — 6 ключевых, с которыми работает фронт (полный перечень всех 17 — в `DIPLOMA.md §4`):

| Сущность | Что в ней | Кто заполняет |
|---|---|---|
| direction | направления проекта (кофейня, мастерские, шоурум, события) | сотрудники |
| event | мероприятия с датой, ценой, типом, количеством мест | сотрудники |
| product | товары шоурума (керамика, бижутерия, одежда, текстиль) | сотрудники |
| showroom | одна запись с hero-картинкой страницы /showroom | сотрудники |
| event-registration | заявки на мероприятия | автоматически, когда посетитель заполняет форму |
| order | заказы из корзины | автоматически, когда посетитель оформляет покупку |

## Часть 7. CI/CD простыми словами

### Что такое CI/CD

- **CI** (Continuous Integration) — «непрерывная интеграция». Когда мы пушим код в GitHub, автоматически проверяется, что он собирается без ошибок.
- **CD** (Continuous Deployment) — «непрерывный деплой». Если код собрался — он автоматически выкатывается на боевой сервер.

Без CI/CD мы бы каждый раз руками: подключались к серверу по SSH, копировали файлы, перезапускали процессы. Это долго и можно забыть какой-то шаг. С CI/CD — просто пушим в GitHub, дальше всё происходит само.

### Как это у нас сделано

Используем **GitHub Actions** — встроенный в GitHub сервис для автоматизации. Конфигурация лежит в `.github/workflows/deploy.yml` (в обеих репах).

**Триггер:** запускается, когда кто-то делает `git push` в ветку `production`. На остальные ветки (например, `vankrav` для разработки) не реагирует.

**Что делает workflow для фронта:**
```
1. Скачивает свежий код из ветки production
2. Устанавливает зависимости (npm ci)
3. Собирает сайт (npm run build) — получается папка dist/
4. Подключается к серверу по SSH (использует приватный ключ из GitHub Secrets)
5. Копирует dist/ на сервер в /home/nastyasep2004/apps/web/
   командой rsync (синхронизация файлов)
6. Готово — nginx сразу начинает раздавать новый сайт
```

**Что делает workflow для CMS:**
```
1. Скачивает свежий код
2. Подключается к серверу по SSH
3. Копирует исходники в /home/nastyasep2004/apps/cms/
   (исключая node_modules, .env, картинки — они уже на сервере)
4. На сервере выполняет:
   - npm ci          (установка зависимостей)
   - npm run build   (сборка админки)
   - pm2 restart okkolo-cms  (перезапуск Strapi)
```

Длительность: фронт — ~50 секунд, CMS — ~3 минуты (Strapi долго собирает админку).

### Ветки в git

| Ветка | Что в ней |
|---|---|
| `main` | старая, не используется |
| `vankrav` | рабочая ветка разработки |
| `production` | то, что сейчас на проде. **Пуш сюда = автодеплой.** |

Процесс разработки:
1. Делаем изменения в `vankrav`, тестируем локально.
2. Когда готово — мержим в `production` и пушим.
3. Через 1-3 минуты изменения на сайте.

### Секреты для деплоя

В настройках каждого репозитория на GitHub лежат **Secrets** — переменные, которые видит workflow, но не виден в коде:

- `SSH_PRIVATE_KEY` — приватный ключ для SSH-подключения к серверу.
- `SSH_HOST` — `158.160.128.16` (IP сервера).
- `SSH_USER` — `nastyasep2004` (имя юзера на сервере).

## Часть 8. Что на сервере

```
/home/nastyasep2004/
├── apps/
│   ├── web/                  ← фронт (туда GHA-workflow складывает dist/)
│   │   ├── index.html
│   │   └── assets/
│   │       ├── *.js
│   │       ├── *.css
│   │       └── *.jpg, *.webp, *.avif
│   │
│   └── cms/                  ← Strapi (исходники + node_modules + .env)
│       ├── src/
│       ├── config/
│       ├── .env              ← секреты (пароль БД и т.д.) — chmod 600
│       └── public/uploads/   ← загруженные через админку картинки
│
└── .pm2/                     ← pm2 хранит здесь логи и состояние процессов
```

### Что делает nginx (конфиг в `/etc/nginx/sites-enabled/okkolo`)

```
Запрос пришёл на сервер
        │
        ▼
nginx смотрит URL:
├── /                          → отдать index.html из apps/web/
├── /assets/*.js, *.css, *.png → отдать файл из apps/web/assets/
├── /api/*                     → переслать в Strapi на 127.0.0.1:1337
├── /admin                     → переслать в Strapi (это админка)
├── /uploads/*                 → переслать в Strapi (картинки из CMS)
└── /content-manager, /upload, /i18n, /users-permissions, /email,
    /users, /auth, /_health    → всё в Strapi
```

Strapi сам наружу не торчит. Слушает только localhost (127.0.0.1:1337). Поэтому даже если у Strapi была бы уязвимость — снаружи к нему не подключиться, только через nginx.

### Что делает pm2

`pm2` — это **process manager** для Node.js. Запускает Strapi и следит за ним.

```bash
pm2 ls                      # посмотреть какие процессы запущены
pm2 logs okkolo-cms         # посмотреть логи Strapi
pm2 restart okkolo-cms      # перезапустить
```

Если сервер ребутнулся (выключали электричество, или мы сами перезагрузили), `systemd` автоматически запустит `pm2`, а `pm2` — запустит Strapi. Не надо руками заходить и поднимать.

### Бэкапы

Бэкап БД делается командой:
```bash
pg_dump -h 127.0.0.1 -U okkolo okkolo_cms | gzip > backup.sql.gz
```

Сейчас по расписанию не настроено — делается руками перед опасными изменениями (например, перед обновлением Strapi).

## Часть 10. Что мы сделали для доступности (a11y)

Сайт должен работать для людей с ограниченными возможностями. Это требование **WCAG 2.1 AA** — международный стандарт.

Что мы сделали:
- **Семантическая разметка**: `<header>`, `<main>`, `<nav>`, `<section>`, `<article>` — screen-reader понимает структуру.
- **alt-тексты** у всех содержательных картинок.
- **Полная клавиатурная навигация** — все интерактивные элементы можно достать через Tab.
- **Видимый focus** — когда юзер табает, он видит синий контур.
- **skip-link** на сложной странице `/workshops` — кнопка «перейти к списку программ», чтобы не табать через всё меню.
- **Контраст текста** — каждая надпись соответствует норме 4.5:1 (мы это специально проверили инструментом axe-core).
- **target-size** — все кнопки и ссылки минимум 44×44 пикселя (чтобы было удобно тыкать пальцем).
- **Корректные ARIA-атрибуты** в модалках и формах (через библиотеку Radix Dialog).
- **prefers-reduced-motion** — если у юзера в системе включено «уменьшить анимации», мы их отключаем.

Автоматическая проверка через **axe-core**: было 12 нарушений → стало 2 (только незначительные).

> Полный разбор по критериям WCAG (Success Criteria по четырём принципам, с расчётами контраста) — в `DIPLOMA.md §2`. Здесь — список простыми словами, там — формальная таблица.

## Часть 11. Адаптивность (responsive design)

Сайт работает на экранах от 320 пикселей (старый iPhone SE) до 1920+ (большой монитор).

**Подход:** mobile-first. Сначала пишем стили для маленьких экранов, потом через `@media (min-width: ...)` добавляем правила для больших.

**Брейкпоинты** (точки переключения вёрстки):
- 640 px — маленький планшет;
- 1024 px — десктоп;
- 1120 px — переключение карусели направлений на сетку (тут была наша конкретная проблема: на узких десктопах текст карточки «Мастерские» вылезал за рамку);
- 1280 px — широкий монитор;
- 1440 px — экстра-широкий.

Сразу — проверяем на двух главных размерах: 375 px (айфон) и 1440 px (макбук). Между ними ловим проблемы на брейкпоинтах.

## Часть 12. FAQ — что может спросить препод

### «Почему React, а не Vue или Angular?»

React — самый популярный фронтенд-фреймворк, на нём больше открытых компонентов и больше разработчиков на рынке. Если завтра проект захочет нанять нового программиста — React-разработчиков на порядок больше, чем Vue.

### «Что такое SPA и почему вы не SPA?»

SPA (Single Page Application) — это когда сайт загружается **один раз**, а потом все переходы между страницами происходят без перезагрузки, только меняется содержимое внутри браузера.

У нас **частично SPA**: главная страница — это SPA, и React сам рендерит блоки. Но переходы между крупными разделами (`/`, `/events`, `/showroom`, `/workshops`, `/cafe`, `/about` и др.) — это **обычная перезагрузка**, как на старых сайтах.

**Почему так?** Страниц немного, добавлять роутер ради этого — оверкилл. Полная перезагрузка добавляет 200 мс ожидания — пользователь этого не замечает.

### «Что такое REST API?»

REST — это договорённость, как клиент и сервер общаются по HTTP. Каждая сущность имеет свой URL, операции называются глаголами HTTP:

- `GET /api/events` — «дай мне список мероприятий»
- `GET /api/events/5` — «дай мероприятие с id=5»
- `POST /api/events` — «создай новое мероприятие»
- `PUT /api/events/5` — «обнови мероприятие 5»
- `DELETE /api/events/5` — «удали мероприятие 5»

Все ответы в JSON. У нас Strapi автоматически создаёт REST API для каждой сущности.

### «Что такое JSON?»

JSON (JavaScript Object Notation) — формат данных, который выглядит как объекты JavaScript:

```json
{
  "id": 5,
  "title": "Вечер живого джаза",
  "date": "2026-05-29T16:00:00.000Z",
  "isPaid": false
}
```

Удобен тем, что и человек и машина читают одинаково легко.

### «Зачем нужна CMS если можно хардкодить?»

Если бы мы хардкодили мероприятия в коде, добавить новое мог бы только программист: открыть файл, написать, запушить, дождаться деплоя. С CMS сотрудник проекта сам заходит в админку, заполняет форму — через секунду мероприятие на сайте.

### «Что такое контейнеризация (Docker)? Почему не используете?»

Docker позволяет упаковать приложение со всеми зависимостями в «коробку», которая запускается одинаково на любой машине. Это удобно для микросервисной архитектуры и для команд.

Мы **сознательно не используем** Docker:
- у нас один сервер и одно приложение — оверкилл;
- pm2 + nginx справляются и проще в отладке;
- меньше слоёв = меньше шансов сломаться.

Но если проект вырастет и понадобится несколько серверов — Docker станет первым кандидатом.

### «Что такое микросервисы? Вы монолит?»

Микросервисы — это когда система разбита на много маленьких независимых приложений, каждое со своей БД, и они общаются по сети.

Мы — **не монолит и не микросервисы**, мы посередине: **frontend + backend разделены**, но backend один. Это называется **fullstack с отдельным API** или **decoupled architecture** (расцепленная архитектура).

### «Что такое responsive design?»

Это когда сайт адаптируется к ширине экрана. На телефоне видна одна колонка, на планшете — две, на десктопе — три или четыре. Через CSS-медиа-запросы (`@media (min-width: 640px) { ... }`) меняем layout.

### «Что такое доступность (a11y)?»

A11y (accessibility) — это про то, что сайтом могут пользоваться люди с ограниченными возможностями: слабовидящие через screen-reader, слабомоторные через клавиатуру, цветовая слепота через достаточный контраст. Стандарт — WCAG 2.1 AA. Проверяется автоматическими инструментами (например, axe-core) и ручным тестированием.

### «Что такое CI/CD?»

CI (Continuous Integration) — автоматическая сборка и проверка кода после каждого пуша. CD (Continuous Deployment) — автоматическое выкатывание на прод. У нас оба настроены через GitHub Actions: push в `production` → автодеплой.

### «Как у вас защищены секреты (пароли БД и т.д.)?»

1. В коде нет ни одного секрета — всё в файле `.env`, который **не коммитится в git** (он в `.gitignore`).
2. На сервере `.env` имеет права `chmod 600` — читать может только владелец-юзер.
3. SSH-ключ для деплоя хранится в GitHub Secrets — он зашифрован и виден только во время выполнения workflow.

### «Что вы делаете когда сайт сломался?»

1. Открыть GitHub Actions → посмотреть упал ли последний деплой.
2. На сервере: `pm2 logs okkolo-cms` — посмотреть логи Strapi.
3. На сервере: `sudo tail /var/log/nginx/error.log` — логи nginx.
4. Откат: `git revert <коммит>` и push в production → автодеплой выкатит предыдущую версию.

### «Что такое медиа-запросы (media queries) в CSS?»

Это правила вида «применить эти стили, только если экран шире 640 пикселей»:
```css
@media (min-width: 640px) {
  .card { padding: 24px; }
}
```
Так делается адаптивность.

### «Что такое TypeScript и почему он лучше JavaScript?»

TypeScript = JavaScript + типы. Мы указываем что переменная — число (`number`), а функция возвращает строку (`string`). Если где-то ошибка типов — компилятор кричит ещё до запуска. В чистом JS такие ошибки нашёл бы только пользователь.

### «Что делает Vite?»

Vite — это **сборщик** (бандлер). Берёт сотни маленьких файлов нашего кода, упаковывает в один-два JS-файла и один CSS-файл. Браузеру удобнее скачать 2 больших файла, чем 200 маленьких.

Также Vite во время разработки запускает локальный сервер с **hot reload** — когда мы меняем код, страница в браузере обновляется мгновенно.

### «Что такое Tailwind?»

Это библиотека утилитарных CSS-классов. Вместо `<div style="padding:16px; background:white; border-radius:8px">` пишем `<div class="p-4 bg-white rounded-lg">`. Получается компактнее и без необходимости придумывать имена классам.

### «Почему сайт быстрый?»

1. Картинки автоматически конвертируются в AVIF/WebP (новые форматы, в 2-3 раза меньше JPG).
2. Vite собирает минимальный JS-бандл (~100 КБ gzip).
3. Nginx раздаёт статику с gzip-сжатием.
4. Tailwind при сборке выкидывает все CSS-классы, которые мы не используем — итоговый CSS ~12 КБ gzip.
